# 設計思想

Verity は「証明可能なコンセンサスクライアント（Provable Consensus Client）」である。他のクライアントが正しさを*テスト*するのに対し、Verity はそれを*証明*する。本ドキュメントの目的は、機能を列挙したりライブラリを選んだりすることではない。後続のあらゆる判断を決定づける「信念」を明示することにある。二つのもっともらしい設計が競合したとき、より安全なほうが勝つ。Verity にとって安全性の最も確かな裏付けは、仕様への忠実さを*証明可能な形で*示せることだ。

以下のすべては、良いソフトウェアの当たり前の規律——小さな関数、単一責任、明快な命名、巧妙さより単純さ——を前提とする。これらは*下限*であって、思想そのものではない。ここから述べるのは、単に「よく作られた」クライアントと Verity を分かつものである。

## Lean Ethereum との整合

Verity は自らの目標を発明しない。Lean Ethereum からそれらを受け継ぎ、実装のレベルでそれらにコミットする。

- **セキュリティ強化。** Lean Ethereum はコンセンサスをポスト量子・ハッシュベースの署名へ移行させる。Verity は上述のとおり、この移行を構造的なものとして扱う。
- **分散化。** Lean Ethereum は参加の障壁を下げ、一般のステーカーがバリデータを動かせるようにする。Verity が重視する「小さく・再現可能で・panic しない」クライアントは、同じ目的に資する——現実的に動かせ、信頼できるクライアントである。
- **高速なファイナリティ。** Lean Ethereum は、分離され階層化されたコンセンサスにより数スロットでファイナライズする。Verity はそのファイナリティ規則を忠実に実装し、その安全条件を侵してはならないものとして扱う。
- **最小主義。** Lean Ethereum は仕様を検証できるほど小さく保つ。Verity は*実装*を検証できるほど小さく保つ。

この四つの柱に、Verity は自前の第五の柱を加える——**証明可能性（provability）**だ。Lean Ethereum は検証*できる*コンセンサス層を作る。Verity は、その検証を稼働するコードまで貫くクライアントである。

## なぜ「証明可能な」クライアントなのか

Lean Ethereum はコンセンサス層をゼロから再設計する取り組みである。この大きな仕様変更に対してセキュアな実装を提供することが Verity の使命である。
仕様は、単にレビューされるだけでなく形式的に検証できるよう、意図的に最小限に保たれている。これは際立った基盤だ。
しかし、検証可能な仕様があるからといって、正しいクライアントが手に入るわけではない。仕様と実際に動くバイナリの間には実装が横たわっており、現実のコンセンサスバグは常にそこに潜んできた。フィールドの読み違え、遷移における off-by-one、集約のエッジケース、不正な入力での panic。

Verity は、このギャップを埋め、埋め続けるために存在する。その目的は、検証可能な仕様の保証を、バリデータが実際に動かすソフトウェアの中まで余すところなく届けることにある。
実装が仕様に一致すると単に*信じられている*のではなく、一致すると*示されている*状態にするために。これこそ、残りの思想すべてが導かれる唯一の核心だ。

## 根本的な信念

これらは設計原則の上位に位置する確信である。めったに変わらない。原則は、それらを実践するための手段だ。

- **安全性を最優先する。** Verity のあらゆる判断は、まず安全性に答える——コンセンサスが壊れないこと、バリデータの資産が損なわれないこと、不正な入力や攻撃で破綻しないこと。定理証明・メモリ安全性・型安全性は、それ自体が目的ではない。すべてこの最優先事項に仕える手段だ。証明はコアのクリティカルなロジックに対する最も強い保証であり、メモリ安全性と型安全性は、証明がまだ及ばない部分も含めて実装全体を言語レベルで安全に保つ。安全性と、速さや手軽さが衝突するなら、安全性が勝つ。ただしそれは性能を諦める口実ではない。leanMultisig（署名集約・証明生成）や leanMetrics が求める性能水準は満たすべき要件であり、Verity は安全性を保ったままその水準に届く道を探す。

- **leanSpec は実働する真実の源（source of truth）であり、かつ動き続ける。** Python による参照実装である leanSpec は、現存する Lean Consensus の最も権威ある実行可能な定義であり、Verity はこれをプロトコルの基準点として扱う。leanSpec が形状を定めている箇所では、Verity はそれに正確に一致させる。フィールド順序とシリアライゼーションはコンセンサスにとって決定的だ。しかし leanSpec は*参照実装*であって、凍結された完全な権威ではない。その安全性も所与ではない。Verity はそれを Lean による定理証明で検証する。だから leanSpec と食い違っても、Verity が黙って独自路線を採ることはない。多くは Verity 側の欠陥であり、Verity を直す。しかし証明で安全性を示せない、あるいはバグを見つけた場合は、leanSpec 自体を上流で更新して再び一致させる。こうして Verity の形式検証は、実装だけでなく仕様そのものを点検する。Lean Consensus は設計と実装の両面でなお進化を続けており、leanSpec が最新の仕様議論を常に反映しているとは限らない。そのため Verity は、leanSpec を緊密に追いつつも固執はしない。

- **テストより証明を。** 適合性ベクトル（conformance vectors）と相互運用の実行は*下限*である。テストスイートが通るということは、「我々が思いついたケース」が動くことを示すにすぎず、「思いつかなかったケース」については何も語らない。数学的証明が*上限*であり、Verity が自らに課す基準だ。「テストにより正しい」と「証明により正しい」は別の主張である。理想は、すべてを証明し Lean で動かすことだ。しかしパフォーマンスと開発コストは現実の制約であり、すべてを一度に証明するわけではない。だから Verity はコアのクリティカルなロジックから優先的に定理証明し、それを FFI 経由で使えるようにしていく。検証の範囲は、そこから外へ広げていく。

- **検証可能性のための最小主義。** ここで言う「小さく保つ」は美的な好みではない。証明の前提条件である。Lean で書かれるコアが抱える抽象・ジェネリクス・間接化は、ひとつ増えるごとに証明がカバーすべき面積を広げ、コアと Rust ランタイムをつなぐ FFI 境界も複雑にする。だから Verity は、証明対象の面積をプロトコルが許す限り小さく保ち、現実のプロトコル要件が要求したときにのみ構造を加える——将来を見越して先回りで加えることはしない。

- **検証境界はアーキテクチャの第一級の構成要素である。** Verity は、何が証明済みコアの内側にあり、何が外側にあるかを、常に明示する。この境界は設計され、文書化され、防衛されるものであって、後から発見されるものではない。コアに入り込むコードはコアの基準で律せられる。境界の外のコードは、コアにクリーンで型付けされた入力を供給し、その出力をネットワークへ運ぶために存在する。

## 設計原則

これらは上記の信念から直接導かれる。それぞれを「立場」として述べ、それが検証可能性にどう資するかの理由を添える。

- **純粋で決定論的なコンセンサスコア。** 状態遷移とフォークチョイスは、入力の純粋関数として表現され、隠れた状態・時計・ロック・スケジューリングを持たない。並行性と入出力はシステムの周縁へ押し出す。証明が推論できるのは決定論的な関数だけだ。コンセンサスロジックが共有可変状態やタスク順序に依存した瞬間、それは完全には検証できないものになる。コアを純粋に保つことこそが、そもそも証明を可能にする。

- **巧妙さより明示性を。** Verity は、マクロ生成のポリモーフィズムや深いジェネリクス階層よりも、具体的で名前のついた型と素直な制御フローを好む。これは Lean のコアでも、それを取り巻く Rust でも変わらない。コードは、レビュアーが、そして証明が、あらゆる値の正確な形状と各ステップの証明責務を見て取れるように読めるべきだ。構造を隠す巧妙さは二重のコストを払う。コードを推論するときに一度、そしてコアと Rust ランタイムの間で型を揃えるときにもう一度。

- **証明契約としての panic-freedom。** コンセンサスコアについての証明は、周囲のプログラムが予期せぬ入力で依然として異常終了しうるなら、無価値だ。検証されたパスの内側では、失敗しうる操作はクラッシュではなく明示的な結果（result）を返し、ランタイムは証明が記述する挙動から逸脱できないように構築される。突然の終了は、どこか別の場所で処理される「許容できる最後の手段」ではなく、正しさの失敗として扱われる。

- **メモリ安全性と型安全性で実装全体を守る。** 安全性は、形式証明が届く範囲だけの話ではない。安全性を言語レベルで支えるのがメモリ安全性と型安全性だ。Verity はメモリ安全で強く型付けされた言語の上に築く。コアでは `unsafe` を避け、メモリ破壊・解放後使用・データ競合といった未定義動作を締め出す。FFI など `unsafe` が要る箇所は、小さく監査された境界に閉じ込める。型は不正な状態を表現できないように設計し、ありえない値はそもそも構築させない。証明がまだ及ばないコードも、言語が安全に保つ。

- **証明された不変条件を映す算術。** コンセンサスコアの数値演算は Lean で書かれ、その境界が Lean で証明される。オーバーフロー・アンダーフロー・切り捨ては、下流で捕捉すべきランタイム上の不意打ちではない。それらは証明が排除する条件だ。コアの外で Rust が同じ値を扱うときも、その算術は証明された境界を尊重する。

- **再現性とサプライチェーンの完全性は証明の一部である。** ソースコードについての証明は、そのソースから再ビルドできないバイナリや、依存関係を監査できないバイナリについては何も語らない。Verity は、再現可能なビルドと、規律ある・ピン留めされた・監査可能な依存関係集合を、運用上の後付けではなく正しさの保証の延長として扱う。信頼の連鎖は、仕様から証明を経て、バリデータが動かす成果物（artifact）まで貫かれる——そのどの環も暗黙のままにはしない。

- **共有された証拠による適合性。** 適合性ベクトルは leanSpec が定める。leanSpec はその適合性テストを自ら備えており、Verity はこの同一のベクトルを実行中のクライアント（Lean のコアと、それを呼ぶ Rust）に流し、leanSpec と挙動が一致することを確かめる。テストも証明も同じ leanSpec を物差しにするので、両者は食い違わずに補強し合う。フィクスチャの先には、稼働中の devnet で他クライアントと相互運用することがあり、これこそ最も過酷なテストだ。Verity は、この試練を通過することを適合性の真の尺度とみなす。

- **ポスト量子セキュリティは構造的である。** Verity の署名はハッシュベースであり、その集約は証明ベースである——プロトコルが要求するとおりに。これは後付けできるオプションではなく、設計を支える要（かなめ）だ。秘密鍵のマテリアルは、それが本来そうである「機微で状態を持つリソース」として扱われ、メモリ上で保護され、安全に永続化される——実在のバリデータがステークするクライアントにとって、ここを誤ることは許されないからだ。


## Verity が意図的に拒むもの

何をするかを述べることと同じくらい、何をしないかを述べることは重要だ。そして既存の Rust クライアントが、そのトレードオフを具体的にしてくれている。

- **構造を隠す、マクロ生成のフォーク・ポリモーフィズム。** 単一の宣言から多数のプロトコル変種を合成するのは強力だが、結果として生じる型は読みにくく、解析しにくく、形式モデルと整合させにくい。Verity は関心ごとに明示的な定義を好み、共有する振る舞いは明快な抽象で表現する。
- **後方互換性のシム。** Lean Ethereum は devnet 間のクリーンな破壊によって前進する。Verity は廃止されたプロトコル版のための互換レイヤを溜め込まない。現在の仕様を追い、古い形状は手放す。
- **panic を許容すること。** クラッシュをグローバルな安全網で吸収することに頼るのは、「コアはクラッシュしえない」と証明することと両立しない。Verity はその姿勢を採らない。
- **浮動または未監査の依存関係。** ピン留めされていないバージョンやレビューされていない上流は、ソースと成果物の間の信頼の連鎖を断つ。Verity はそれらを受け入れない。
- **検証可能性を引き換えにする最適化。** パフォーマンスは重要だが、もはや推論できないコアと引き換えにはしない。Verity は、検証境界の内側でのみ、あるいはモデルとの対応を保つ形でのみ最適化し、しかも現実のボトルネックが示されてからのみ行う。
- **無制限のリソース増加。** 上限のないキューやバッファは、負荷を障害へと変える。Verity はハッピーパスを当然視せず、明示的なバックプレッシャと有界なリソース使用を前提に設計する。

## KISS・SOLID・通常の規律についての注記

これらの原則は前提であって、論じる対象ではない。Verity は関数を小さく保ち、関心を分離し、単純な設計を好む——だがそれは、ある特定の理由のためだ。すなわち、単純さと明快な境界こそが、検証境界を防衛可能にし、Lean で書かれたコアを小さく証明しやすく保つ。一般的なベストプラクティスと検証可能性上の懸念が別の方向を指したとき、決めるのは検証可能性だ。馴染みある諸規律は手段であり、証明可能なクライアントが目的である。

## ステータス

Verity は実装前（pre-implementation）である。本ドキュメントは、アーキテクチャ・クレート構成・将来書かれるすべてのコードが従うべき北極星だ。Lean Consensus もその参照実装もなお動いている最中であり——プロトコルの設計は活発に議論され、leanSpec もそれに伴って変化する——ゆえに本ドキュメントは、仕様が前進するにつれ、また Lean 4 検証の取り組みが「真の境界はどこか」を教えてくれるにつれ、進化していくことが見込まれる。その中心的なコミットメントは変わらない。稼働するクライアントは、仕様に一致すると単に信じられるのではなく、一致すると示される。
